# CloudArt — production deployment log (Option A)

**Purpose.** A step-by-step record of how CloudArt was put on AWS, written so you can *reverse-engineer* it. For every stage you get
**what** was done, **why** it was done that way, the **commands** (they live in re-runnable scripts under
[`deploy/aws/`](../deploy/aws/) and in Terraform under [`deploy/terraform/`](../deploy/terraform/)), what the **result** was,
how it was **verified**, how to **undo** it, and every **error** met on the way with its cause and fix.
The design and the comparison with the other options are in [`deployment-options.md`](deployment-options.md); the resource inventory
and teardown are in [`aws-resources.md`](aws-resources.md).

**Suggested reading order for reverse-engineering:** section 1 (what exists) → section 2 (decisions) → the stages in order →
section 5 (how requests and deployments flow) → the Terraform README → the scripts, from `lib.sh` outward.
No secret appears in this document: passwords and the origin secret are generated by Terraform and live only in Terraform's
encrypted state and in one encrypted SSM parameter.

## 2. Decisions and risks

| # | Item | Decision and why |
| --- | --- | --- |
| D1 | **Option A** (one EC2 server) | Cheapest design that is still properly AWS. Comparison in `deployment-options.md`. |
| D2 | **Terraform, in modules** | You asked for Terraform and then for the best practice of separate modules. Resources are described as code, tagged automatically, and can be torn down with one procedure. |
| D3 | **No ECR; the server builds its own image** | The ECR API endpoint cannot be reached from this PC (error E1). We ship the source of an exact git commit through S3 and build natively on the server's ARM CPU. Trade-off: a build takes a minute or two of server CPU. |
| D4 | **Tags** `Project=CloudArt`, `Environment=prod`, `Component=<part>`, `ManagedBy=ClaudeCode` | Your standing rule. `Environment` is `prod` because the dev Cognito pool already uses `dev`. Applied by the provider's `default_tags`, so no resource can miss them. Verified on 30 tagged resources (the only one without `prod` is the old dev pool). |
| D4b | **Mandatory cost tag activated** | The budget filters on `Project`, which only works once that tag is an "active cost allocation tag". Activated with `aws ce update-cost-allocation-tags-status` (stage 9). It changes only billing reports. |
| D5 | **CloudFront → server over plain HTTP** | A `*.cloudfront.net` distribution cannot present a certificate for an EC2 name. The visitor's connection is HTTPS; the hop inside AWS is HTTP, limited to CloudFront by the security group *and* by a secret header the API requires (`ORIGIN_VERIFY_SECRET`), because the CloudFront address list is shared by all CloudFront customers. |
| D6 | **CPU credits in `standard` mode** | A runaway load slows the server instead of producing a surprise bill. Consequence seen in stage 8: right after many builds the credit balance is near zero and the alarm fires. The alarm now waits a full hour. |
| D7 | **CSP is report-only** | The browser logs what the security policy *would* block but blocks nothing. The public pages produced no violations. It is switched to enforcing (`csp_mode = "enforce"`) after a real video lesson has been watched on the live site, because the YouTube player is the part we cannot test without course data. |
| R1 | **The AWS CLI used the account's root keys** | You asked me to continue with the CLI access you have. Root cannot be limited. **Your action:** create an admin IAM user with MFA, switch the CLI to it, then deactivate and delete the root access keys. The server itself never uses keys. |
| R2 | **One server holds the API and the database** | The mitigations are real and tested: daily disk snapshots, nightly dump to S3 with a restore drill that passed, alarms on disk, memory, health, 5xx errors and a missing backup, automatic security updates. |
| R3 | **The account is on the Paid plan, with 0 credits** | The preflight showed `accountPlanType: PAID`. Every resource costs real money (about 16 USD a month). |

## 3. The stages

Conventions: scripts start with `source lib.sh` (sets `set -euo pipefail`, UTF-8, the region, Terraform on the PATH, helper
functions). Read-only calls are retried; creating calls are made safe by Terraform's state or by "look first, then create".

### Stage 0 — Preflight (read-only) · `deploy/aws/00-preflight.sh`

**What.** Who are we, what plan is the account on, can we reach each AWS service we need, is the instance type offered, which
Amazon Linux image is current.
**Why.** Earlier checks had shown RDS/ECR calls dropping and App Runner disabled. Knowing which services work *before* building avoids a
surprise half-way.
**Result.** Root identity (R1); plan **PAID**, credits 0 (R3); EC2, S3, SSM, IAM, CloudFront, CloudWatch, SNS, DLM, Budgets, Cognito all
answer; **ECR does not** (E1); `t4g.small` offered; image id found through the public SSM parameter
`/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-arm64` (using the parameter means every new server starts from the current
patched image instead of a hard-coded old one).
**Undo.** Nothing to undo.

### Stage 1 — Terraform state bucket · `deploy/aws/01-bootstrap-state.sh`

**What.** One S3 bucket `cloudart-prod-tfstate-589531223229`: all public access blocked, encrypted, versioned, HTTPS-only, tagged.
**Why.** Terraform records what it built in a *state* file that contains generated passwords, so it must not sit in OneDrive or git. A
private versioned bucket also lets us recover an older state. Terraform needs the bucket before it can run, so this is the one thing made by hand.
Locking uses S3's own lock file (`use_lockfile`), so no DynamoDB table is needed (Terraform ≥ 1.10).
**Verify.** The script prints the access-block flags (all true), versioning `Enabled` and the four tags.
**Undo.** `aws s3 rb s3://cloudart-prod-tfstate-589531223229 --force` (only after `terraform destroy`; it holds the record of what exists).

### Stage 2 — Install Terraform

**What.** Downloaded Terraform 1.17.2 from `releases.hashicorp.com`, verified its SHA-256 against the published `SHA256SUMS`, unzipped
`terraform.exe` into `C:\Users\nimes\tools\terraform` (outside OneDrive). `lib.sh` adds that folder to the PATH for the scripts; no
system setting was changed.
**Why.** You asked for Terraform; verifying the checksum protects against a corrupted or tampered download.
**Undo.** Delete the folder.

### Stage 3 — Terraform code, first as flat files, then as modules

**Order of events (for honesty):** the first version was a single flat folder (it created everything in one apply). You then asked
for best practice with modules; stage 10 shows that refactor. Both are described here as one design.

**Module layout** (details in `deploy/terraform/README.md`):

| Module | Resources (count) | Job |
| --- | --- | --- |
| `network` | VPC, 2 subnets, internet gateway, route, S3 gateway endpoint, locked default SG, API SG (13) | where the server lives and who may reach it |
| `storage` | 3 buckets + public-access block, ownership, encryption, versioning, lifecycle, TLS-only policy (21) | files and backups |
| `auth` | Cognito pool + client (2) | login |
| `server` | IAM role/policy/profile, Elastic IP, data disk, instance, attachment (12) | the machine and its permissions |
| `cdn` | origin secret, access control, SPA function, headers policy, distribution, site-bucket policy (10) | one HTTPS address |
| `settings` | DB password + the SSM parameter (2) | secrets and `.env.prod` |
| `operations` | SNS, budget, log group, snapshots, 8 alarms, log filter (19) | monitoring and backups |

**Key design choices and their reasons** (each is also a comment in the code):

* *Dedicated VPC `10.20.0.0/16`, no NAT gateway.* The account already has other projects' networks; a NAT gateway would add ~35 USD a month.
  The server sits in a public subnet protected by its security group.
* *Security group: port 80 from the CloudFront prefix list only; no SSH rule.* Management is through SSM Session Manager (logged, no open port).
* *No access keys on the server.* An IAM role limited to: the two upload folders, the backup and release folders, one SSM parameter, the log group, and
  metrics in one namespace. **IMDS hop limit 2** is required because the API runs in a container one network hop further away; with the default of 1 the container could not obtain its credentials (this was designed in, not discovered by failure).
* *Separate encrypted data disk with `prevent_destroy`,* instance `disable_api_termination`, Cognito `deletion_protection`: a mistaken `destroy` cannot delete data.
* *`lifecycle.ignore_changes = [ami, user_data]` on the server:* a newer AMI or an edited boot script must never rebuild the machine that holds the database.
* *The site is served by a CloudFront Function, not "custom error pages":* error pages would also turn the API's real JSON 404 answers into the website page. The function sends any path
  without a file extension to `/index.html`.
* *`/api/*` is never cached and forwards all headers* (the file upload needs `X-File-Name` and `Authorization`).

**Commands.** `cd deploy/terraform/environments/prod`, then `terraform init`, `terraform validate`, `terraform plan -out=tfplan`, `terraform apply tfplan`
(or use `deploy/aws/tf.sh`).
**Result.** First plan: **64 to add, 0 to change, 0 to destroy.** Apply: all 64 created on the first attempt in about 4 minutes (CloudFront took 3).
**Errors in this stage:** E4 (a description with a forbidden character, caught by `terraform validate`), E5 (my shell heredoc for the files broke).
**Undo.** See section 7 (Teardown).

### Stage 4 — Server first boot · `modules/server/templates/userdata.sh.tftpl`

**What.** On first boot the machine installs Docker and the Docker Compose plugin (pinned version, checksum verified), makes a 2 GB swap file, formats the empty data disk (only if it
has no file system), mounts it at `/data`, installs the nightly backup script and its systemd timer, the CloudWatch agent (disk and memory numbers), and automatic *security* updates.
**Why.** The script contains no secrets; the application and its settings arrive later (stage 5). Swap turns a sudden out-of-memory kill on a 2 GiB machine into a slowdown.
**Result.** The first run **stopped part-way** (E8). After the fix: `/data` mounted (20 GB, xfs), swap 2 GB, backup timer scheduled for 20:30 UTC, agent and automatic updates active, IMDSv2 enforced (a token-less request answers 401).
**Verify.** `deploy/aws/ssm-run.sh 'df -h / /data; swapon --show; systemctl is-active docker cloudart-backup.timer amazon-cloudwatch-agent dnf-automatic.timer'`.
**Errors.** E8.

### Stage 5 — Ship the API · `deploy/aws/05-ship.sh` → `deploy/server/deploy.sh`

**What.** The local script archives the *committed* source (`git archive`, so what is deployed is exactly what is committed; the commit id names the release), uploads it to the backups bucket under
`artifacts/`, and asks the server (SSM Run Command) to run `deploy/server/deploy.sh <release>`, which: downloads the encrypted settings from SSM and writes `/opt/cloudart/.env.prod` (mode 600, Unix line endings, refuses a file with carriage returns) →
builds the Docker image natively on the server → starts PostgreSQL and waits until healthy → applies database migrations from the **new** image before the new API starts → seeds the categories (idempotent) → starts the API and waits for health →
**only then** tags the image `latest` (so a failed deploy never changes what a restart would run) → removes old images and releases.
**Why each choice.** *Settings from SSM:* the file is created on Linux, avoiding the Windows carriage-return problem (E9) for secrets. *Migrate before start:* the old API keeps serving until the new one is ready. *Seed idempotent:* safe to run on every deploy.
**Result (final run).** 3 migrations applied to the empty database; seed created 8 service categories and 7 course categories; liveness `{"status":"ok"}`; database `up`; direct request without the secret header → **403**.
**Verify.** The script prints each check; `docker ps` on the server shows `api` and `db` healthy.
**Rollback.** `deploy/aws/ssm-run.sh 'cd /opt/cloudart && docker images cloudart-api; API_IMAGE=cloudart-api:<older-release> docker compose --env-file .env.prod -f docker-compose.prod.yml up -d api'` (the two previous images are kept).
**Errors.** E10 (archive path), E12 (log streams), E13 (Prisma/openssl, two steps). Each failed attempt left the previous release running.

### Stage 6 — Publish the website · `deploy/aws/07-frontend.sh`

**What.** Builds the React app with `VITE_API_URL=/api/v1`, uploads files under `assets/` (they have a hash in the name) with a one-year cache, uploads everything else with a 5-minute cache and `index.html` with `no-cache`,
corrects file types, and invalidates `/index.html` and `/`.
**Why.** The site and the API share one address, so the API is a relative path (no CORS). Hashed files can be cached forever; the page that points at them must always be re-checked.
**Verify (from outside).**

| Check | Result |
| --- | --- |
| `/` | 200 `text/html` |
| `/services/abc` (a React route) | 200 `text/html` (the app page) |
| `/api/v1/health` | `{"status":"ok"}` |
| `/api/v1/no-such-route` | 404 **`application/json`** (not the website page) |
| `/api/v1/users/me` without login | 401 |
| `http://13.233.62.38/…` directly to the server | no answer (security group) |
| `.js` / `.css` types | `text/javascript` / `text/css` |
| Security headers | HSTS, `X-Frame-Options: DENY`, `nosniff`, referrer policy, permissions policy, CSP **report-only** |

### Stage 8 — Browser check of the live site · `frontend/e2e/prod-smoke.spec.js`

**What.** Playwright against the live address, desktop and mobile: public pages load with no console errors, no failed requests, **no Content-Security-Policy violations** and no sideways scrolling; React routes survive reload; protected pages send a visitor to log in; an unknown page is

**Result.** 6 of 6 pass.

### Stage 9 — Backups, restore drill, alarms, budget

* **Nightly dump** (`cloudart-backup.timer`, 02:00 India) → `s3://…-backups-…/db/`. Kept 30 days. After each upload it sends a `BackupSuccess` metric; an alarm fires if a day passes without one.
* **Daily disk snapshot** of the data disk (AWS Data Lifecycle Manager), keep 7.
* **Restore drill** (`deploy/server/restore-drill.sh`): newest dump → throw-away database → row counts compared with the live database → throw-away database dropped.
  **Result: PASSED** (`service_categories` 8/8, `course_categories` 7/7, `_prisma_migrations` 3/3, the rest 0/0). *A backup that has never been restored is only a hope.*
* **Alarms** (8, all to the SNS topic): hardware failure (**also repairs the server automatically**), OS not responding, CPU credits, disk `/` and `/data` over 80 %, memory over 90 %, a missing backup, 5xx errors.
  Disk/memory alarms use `treat_missing_data = breaching`, so a dead monitoring agent is an alarm, not silence. I checked the exact metric dimensions the agent publishes (`InstanceId`, `path`, `fstype=xfs`) against the alarm definitions: all states `OK`.
* **Budget** `cloudart-prod-monthly` 25 USD, alerts at 80 % actual and 100 % forecast, filtered to `Project=CloudArt` (needs the cost tag activated: done).
* **Alarm behaviour to know about:** `cpu-credits-low` was in ALARM after the day's many builds (balance 0.9 → 3.6, average CPU only 5–8 %). It is a true signal on a new server and clears itself as credits recover (24 an hour). The rule was changed from 15 minutes to one hour so a normal deploy does not raise it.
* **E-mail delivery of alerts needs one action from you** (section 8).

### Stage 10 — Refactor into modules (zero change to AWS)

**What.** The flat Terraform files were split into the seven modules above under `environments/prod`. Because real infrastructure already existed, renaming resource addresses would have made Terraform plan to
**destroy and recreate everything, including the database disk.** A `moved` block per resource (`environments/prod/moved.tf`) tells Terraform each resource is the same object at a new address.
**Method and proof.** (1) Baseline `terraform plan` before touching anything: *No changes.* (2) After the split: **0 to add, 0 to change, 0 to destroy** with 64 "has moved" lines. (3) Applied; (4) the next plan: no changes; (5) the server kept instance id `i-0bfc411e093297906`
and IP `13.233.62.38`; (6) the smoke test passed again on the refactored state.
**Design points that mattered:** outputs carry ordering (`site_bucket_id` waits for the public-access block; `public_subnet_ids` waits for the internet gateway and route) because `depends_on` cannot name a variable; the CloudFront secret is created inside the `cdn` module and exported (sensitive) to `settings`, which avoids a module cycle;
the site-bucket policy lives in `cdn` because it needs the distribution's ARN; variables have types, descriptions and `validation` (for example the server size must be an ARM type because the boot script installs ARM binaries).
**An automated security scan (Trivy) was attempted and blocked by the permission system** (it pulls and runs a third-party container image over your code), so it was not run. A manual review was done instead (below). You can run it yourself:
`docker run --rm -v "<path>/deploy/terraform:/src:ro" aquasec/trivy config /src`.
**Manual review notes.** Known and accepted: the server's security group allows all outbound traffic (it must reach S3, Cognito, package repositories and SSM; a NAT-less design cannot restrict by destination); CloudFront-to-server is HTTP (D5); the S3 buckets use SSE-S3 rather than a customer KMS key (adds cost and a failure mode, no extra protection for this threat model); no VPC flow logs and no WAF (cost; the API has its own rate limits).

## 5. How things flow

**A visitor opens a lesson.** Browser → CloudFront. `/services/12` has no file extension, so the CloudFront Function answers `index.html`; the browser loads the hashed JavaScript from S3 (cached at the edge for a year).
The app calls `/api/v1/...` on the same address; CloudFront does not cache it, adds `X-Origin-Verify`, and forwards to the server on port 80. The security group admits only CloudFront; the API's first middleware refuses any request without the secret.
Express reads the real visitor address (`TRUST_PROXY=1`), verifies the Cognito token, and talks to PostgreSQL over the Docker network.

**A file upload.** The browser sends the raw file with `X-File-Name` to `/api/v1/service-requests/<id>/attachments` → the API checks the file's real type from its bytes, writes it to the private uploads bucket through the server's IAM role (encrypted, never overwriting an existing key), and stores only the generated key. Downloads go back through the API, which checks ownership and sends `Content-Disposition: attachment`.

**A deployment.** `05-ship.sh` (this PC) → S3 `artifacts/` → SSM Run Command → `deploy.sh` on the server (stage 5). **A website update** is `07-frontend.sh`. **An infrastructure change** is `tf.sh plan` then `tf.sh apply`.

| Rotate a secret | `terraform apply -replace=module.cdn.random_password.origin` (then `05-ship.sh`); a database password also needs `ALTER USER` inside PostgreSQL first, so plan it |
| Resize the server | change `instance_type` (ARM only); expect a short stop/start |
| Patching | OS security updates are automatic (`dnf-automatic`); a **kernel** update needs a reboot: `ssm-run.sh 'reboot'` in a quiet moment |

## 7. Teardown (deliberately two-step)

Protections are on purpose; to destroy everything:

1. In `environments/prod/terraform.tfvars` set `cognito_deletion_protection = "INACTIVE"`, then `tf.sh apply`. (This deletes login data when the pool is destroyed: export users first if you need them.)
2. In `modules/server/main.tf` remove `prevent_destroy` from the data disk and set `disable_api_termination = false`; apply.
3. Empty the three S3 buckets **including old versions** (the uploads bucket is versioned): list with `aws s3api list-object-versions` and delete each version, or use the console's "Empty".
4. `deploy/aws/tf.sh destroy`.
5. Delete the state bucket last (`01-bootstrap-state.sh` made it).
6. Check nothing is left: `aws resourcegroupstaggingapi get-resources --tag-filters Key=Project,Values=CloudArt`.
The old dev Cognito pool (`cloudart-dev-users`) is **not** part of this and stays.
